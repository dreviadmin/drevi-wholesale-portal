## Bug found and fixed: buyer-facing dates were a day behind

The confirmation screen showed **"24 Sept 2026"** for order **DW-2026`0925`-001**.

`submitted_at` is `2026-09-24T19:12:48Z` = **25 Sep 00:42 IST**. The order number is built in
IST (`src/app/cart/actions.ts:184`) and the PDF prints IST (`src/lib/order-pdf.tsx:161`), but
three buyer-facing screens formatted the date with **no `timeZone`**, so they rendered in the
server's UTC.

Every order placed between **00:00 and 05:30 IST** showed the buyer the previous day's date,
while its own order number and PDF said otherwise.

Fixed by adding `timeZone: "Asia/Kolkata"`, matching what the rest of the codebase already does:

- `src/app/order/[id]/page.tsx:33`
- `src/app/account/orders/page.tsx:13`
- `src/app/account/details/DetailsForm.tsx:57`

Gates after the change: `tsc --noEmit` clean, `next lint` only pre-existing warnings,
`vitest run` 202/202 pass. **Not deployed** — it's sitting in the working tree for you to
review and ship.

## Observations, not bugs

- **No size selector anywhere.** Size is baked into the SKU (`DD-LEH-FLR-077-`**`L`**`-GLD`),
  so a buyer picks quantity only. This is the same thing behind your "why are some products
  pushed in just one size" question — worth deciding whether buyers should be able to request
  a different size.
- **SKU appears twice on catalog cards** — once overlaid on the photo, once as text under the
  title. Harmless, slightly redundant.
- **"In Stock" shows on the order confirmation.** You had these badges removed from the
  catalogue; they still render on the confirmation and in the order `items` snapshot
  (`stock_state: "ready"`). Different surface, so possibly intended — flagging in case not.
- **No WhatsApp fired.** `INTERAKT_API_KEY` is unset in production, so `sendOrderConfirmation`
  and `sendOrderAlert` both logged and skipped. Once AiSensy is wired, this same flow will
  start messaging Rakesh and the buyer — worth knowing before the first real order.

## Found by reading the code, verified in source

These came out of a full read of the buyer-facing flow, not the click-through. Each is quoted
with the line that proves it.

**1. The minimum-order error tells buyers to do something they cannot do.**
`src/app/cart/actions.ts:151` blocks submit with:

> "Some items are below their minimum order quantity. Adjust them (or request a special
> quantity) before submitting."

There is a `special quantity request` server action (`src/app/cart/actions.ts:103`), but no
buyer-facing control anywhere in `src/app/cart/` or `src/components/` invokes it. The minimum
itself is never displayed on any buyer screen either. So a buyer hits a wall, is told to use a
button that does not exist, and is not told what the minimum is. **This will generate calls to
Rakesh.** I could not trigger it in testing because no product in the test cart had a minimum
set — worth confirming which products do before the blast.

**2. Quantity is silently clamped for limited stock.**
`src/app/cart/actions.ts:53` — `return cap != null ? Math.min(q, cap) : q;`
A buyer asking for 10 of something with 3 on hand gets 3, with no message. The number simply
changes back after the cart refreshes.

**3. The login field is labelled "Username or Email" but must be a bare username.**
`src/app/login/actions.ts` appends `@buyers.drevifashion.com` to anything without an `@`. A
buyer who types their own Gmail gets "Invalid username or password." Confirmed working in this
test: `zzqatest` signs in, the synthetic address is never shown. The walkthrough video covers
this explicitly because it is the most likely first-contact failure.

**4. No self-serve password reset.** `/forgot-password` opens a pre-filled WhatsApp message to
Rakesh on the wholesale line (+91 99300 86178, per the WhatsApp template; changed 27 Sep). No email reset exists. Also covered in the video.
